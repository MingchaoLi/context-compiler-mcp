# 对抗审查记录

对抗审查用于降低 Builder、主控和连续成功 QA 共同产生的 automation bias。它不负责把当前方案补得更完整，而是攻击那些看似合理、但尚未被证据证明的工程判断。

## 与独立 QA 的区别

- 独立 QA：实现是否满足当前工单及其验收条件。
- 对抗审查：当前工单是否值得做、顺序是否必要、blocker 是否真实、是否存在更小的验证路径。

两者不能互相替代。QA 通过不证明架构判断正确；对抗审查的 `Challenge` 也不自动证明实现有缺陷。

## 申请时机

主控可以在以下关键节点申请一次独立对抗审查：

- 完成一个路线图阶段，准备决定下一阶段投入；
- 准备引入 provider、network、credential、host、UI 或新的运行时边界；
- 连续多个工单沿同一 Builder 判断推进并通过 QA；
- 声称某组件是继续推进所必需的 blocker；
- 评估指标或 fixture 即将成为重大决策依据；
- 预计新增大量复杂度，但核心假设仍可用更小实验验证。

不要求每个提交或每个工单都执行。主控应以关键决策风险为依据申请，避免把审查本身变成流程负担。

## 独立性与边界

- Reviewer 不是 Builder、实现 QA 或方案设计者，不继承其结论。
- 默认只读，不修改代码、文档或 Git，不接管修复。
- 必须固定候选提交和工作树状态，并遵守仓库最小上下文规则。
- 必须区分事实、推断和建议；证据不足时明确写证据不足。
- 必须给出具体 counterexample，而不是泛化风险。

## 最小输出

- `Verdict`：`Agree`、`Agree with reservations`、`Challenge` 或 `Insufficient evidence`。
- `Facts`：仅列可验证事实。
- `Strongest challenge`：最重要的 1–3 项，包含反例和证据位置。
- `Cheaper path`：能否以更低成本验证同一核心假设。
- `Falsification`：什么证据能推翻 Builder，也能推翻 Reviewer 自己。
- `Residual uncertainty`：未覆盖平台、数据或运行路径。

## 处置

Reviewer 不决定路线图。主控根据记录选择：

1. 反例成立且影响下一决策：创建一个有界补证或修复工单；
2. 风险真实但当前可接受：记录接受理由和重新审查触发点；
3. 证据推翻反对意见：记录撤回理由并继续推进；
4. 证据不足：先执行更小实验，不直接扩大架构。

每次审查使用独立文件，命名为 `AR-YYYY-MM-DD-<milestone>.md`。
