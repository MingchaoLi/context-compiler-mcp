## Facts

- ST-01 前已有 `ExtractorTransport`、`StrictStateExtractor`、严格 Delta parser、Reducer 和 Assembler，可用临时 transport 或人工 Delta 做首轮语义实验。
- ST-02 直接从 fixture 接受初始 `context_items`、relations 和 headlines，代码不依赖 ST-01 的 durable prepare/apply。
- ST-02 对空的正向 probe 指标返回 `1`，空 reopening 返回 `0`；测试固定了这一 vacuous pass 语义。
- ST-02 的 `passed` 检查 D2 绝对质量阈值和相对 D0 的压缩率，没有要求 D2 优于或不劣于 D1。
- `current_input` 总会进入 D2 输出；如果 probe 文本也出现在当前输入中，retention 指标可能无法证明 typed state 提供了价值。
- ST-03 测试 worker 返回预制 Delta，不执行真实语义抽取。ST-03 主要验证 subprocess IPC、错误净化、生命周期和原子 apply。
- runtime 在 extraction 前持久化 preparation；preparation 表由触发器禁止 update/delete。
- formal host、自动 headline 和隐式更新继续延后，不妨碍用临时外部实验验证核心假设。

## Strongest challenge

### 1. ST-02 是可重复测量器，但尚不是可信决策门

Reviewer 构造了三个反例：

- 无 state、headline、recall 且四组 probe 全空的 suite，在质量阈值设为最严格值时仍可 `passed=true`。
- D1 与 D2 五项质量相同，但 D1 为 31 tokens、D2 为 100 tokens 时，runner 仍可 `passed=true`。
- `context_items=[]`，只在 `current_input` 重复 constraint probe 时，D2 仍可报告 constraint retention 为 `1`。

这些反例说明“确定且可重复”不等于“能判断 D2 是否值得”。

证据位置：`src/evaluation.ts` 的输入组装、空集合指标与 `passed` 计算；`test/evaluation.test.ts` 的空标签语义测试。

### 2. ST-01 不是 ST-02 或首轮核心实验的技术 blocker

一个临时 in-process transport 或人工 Delta 可以直接完成“原始会话 → typed state → D2 → D1/D2 比较”，ST-02 也支持直接注入 typed state。durable prepare/apply 的主要价值是跨进程重试、并发 revision 和持久化快照安全，这些能力可能最终需要，但不是隔离验证 assembler/状态表示假设的必要条件。

### 3. ST-03 增加 IPC 可靠性证据，但没有增加抽取语义证据

ST-03 相比“临时 provider + 手工 prepare/apply”多证明了进程机制，而非 Context Compiler 的语义效果。

Reviewer 还复现了一个持久化风险：连续三次 extraction failure 后 state revision 仍为 `0`，但留下 3 条、共 1296 bytes 的 preparation snapshot；删除操作被 immutable trigger 拒绝。长期失败或合法空 Delta 可能持续累积完整快照。目前没有明确的有界保留策略。

证据位置：`src/runtime-state-update.ts` 的 prepare-before-extract 顺序；`src/state-store.ts` 的 preparation immutable triggers。

## Cheaper path

1. 使用多组真实或脱敏 transcript，人工标注 typed state、headline 和非空、带 provenance 的 probes。
2. 直接调用现有 Assembler，先验证 D2 是否在同等质量下稳定优于 D1。
3. 使用一次性外部 provider 脚本或 in-process `ExtractorTransport` 跑严格 parser 和 Reducer；需要时人工串接 prepare/apply。
4. 只有语义效果成立后，再决定是否继续投资 durable preparation、通用 subprocess transport 和 host integration。

## Falsification

可推翻 Builder 判断的证据：

- vacuous suite 通过；
- probe 被 `current_input` 污染；
- D1 同质且更短时 D2 仍通过；
- ST-02 对 ST-01 没有代码依赖；
- 失败 preparation 无有界回收路径。

可推翻 Reviewer 反对意见的证据：

- 预注册、非空、按 state 类型和 provenance 绑定的多会话 corpus；
- D2 相对 D1 的显式非劣或优越门槛；
- 独立标注或下游模型任务结果；
- 真实 extractor 的精度和失败率数据；
- 证据表明 durable/stdio 路径发现了会改变核心决策、且更小实验无法暴露的问题；
- preparation snapshot 的明确有界保留机制。

## Residual uncertainty

- 未运行真实 provider、网络或 formal host，不能断言核心架构无效；结论仅为当前证据未证明推进顺序和复杂度必要。
- 未从 macOS / Node.js 25 结果推断 Windows 或精确 Node.js 24。
- 人工 fixture 可能低估并发、崩溃恢复和 provider 隔离的最终价值；这些能力可能最终需要，但尚未证明现在必须。
